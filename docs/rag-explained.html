01 The mental model

The model has never read
your documents.

There is no fine-tuning step. On every question Bloo runs a database query, takes the four best passages, and hands them to a model with one instruction: answer only from these. The corpus is data, not weights — so publishing and unpublishing are instant.

Common belief

RAG means giving the model all the documents.

  • Cost and latency scale with the size of the corpus.
  • Answers cannot be audited: nothing says which sentence supported a claim.
  • Unpublishing a document changes nothing — it is already in the prompt.
What actually runs

RAG means ranking 150,000 chunks down to four.

  • Retrieval quality sets the ceiling on answer quality.
  • Citations are substrings of chunks, not claims generated by a model.
  • Publishing is a WHERE clause: one view, one rule.
Retrieval decides whether the answer is right. The model only decides whether it reads well.

03 Ingestion

Turning a PDF into something
a database can argue about.

The breadcrumb is not decoration. A chunk that says “the fee is Rs 48,000” is ambiguous on its own. Prefixing Fees › Hostel › Refund policy restores the context — and because the prefix is embedded too, it changes what the vector means.

3.2 Embedding

One model on both sides.

A chunk becomes 384 floating-point numbers. So does the question. Cosine similarity is only meaningful if both came from the same weights — which is why the ingest path and the query path share one Embedder.

dim 0384 floats · normalizeddim 383
// crates/bloo-rag/src/embed.rs trait Embedder { fn dim(&self) -> usize; // 384 — must match vector(384) async fn embed_documents(&self, texts: &[String]) -> Result<Vec<Embedding>>; async fn embed_query(&self, text: &str) -> Result<Embedding>; }
a 2-D sketch of a 384-D space

The question lands near the hostel cluster without sharing a single keyword with it. That is the whole reason dense retrieval exists — and the reason it misses things like CS-301 or ₹48,300, which only lexical search preserves.

the gate

Publishing is a WHERE clause.

A document moves processing → ready → published. Ready is not searchable. Every retrieval query reads one view; there is no second path that could leak an unpublished file.

CREATE VIEW searchable_chunks AS SELECT c.*, d.title, d.kind, d.canonical_url FROM chunks c JOIN documents d ON d.id = c.document_id WHERE d.status = 'published' AND (d.valid_until IS NULL OR d.valid_until > current_date);
idempotence

The same bytes are only ingested once.

Upload is content-addressed: sha256 → ./data/raw/{hash}.{ext}, and documents.file_hash is unique. Re-uploading a file returns the existing document with duplicate: true — no new vectors, no new job.

Deleting is a cascade: chunks go with the document, and the raw file is removed. The assistant stops citing it on the next query, not the next deploy.

Unpublishing is the same operation in reverse: one status update, and the view stops returning those chunks on the very next question.

4.2 Hybrid retrieval

Two search engines that disagree — and that is the point.

dense · pgvector

Meaning, not words

A 384-d vector per chunk, HNSW index, cosine distance. Finds “a cheap place to sleep” in a passage about hostel fees, with no shared keywords.

fails at: exact strings. Course codes, roll numbers, ₹ amounts, section names, dates written once and never again.
lexical · tsvector

Words, exactly

A generated tsv column, GIN index, ts_rank_cd. Keeps CS-301, ₹48,300 and 12/03/2026 intact because the config is simple, not english.

fails at: paraphrase. Ask “cheap place to sleep” and it will never return a chunk that only says “hostel”.
RRF(d) = Σ 1 / (60 + rankᵢ(d))
Reciprocal Rank Fusion, k = 60. One SQL statement. Only ranks are used — the two lists never need their scores normalised, which is why cosine and ts_rank_cd can coexist.

The last row is the non-obvious property: agreement beats a single first place. Rank 40 in both lists scores .0200, more than rank 1 in one list (.0164). RRF rewards independent confirmation.

The SQL, in essence

WITH dense AS ( SELECT id, row_number() OVER (ORDER BY embedding <=> $1) AS rank FROM searchable_chunks ORDER BY embedding <=> $1 LIMIT 40 ), lex AS ( SELECT id, row_number() OVER ( ORDER BY ts_rank_cd(tsv, websearch_to_tsquery('simple', $2)) DESC ) AS rank FROM searchable_chunks WHERE tsv @@ websearch_to_tsquery('simple', $2) LIMIT 40 ), fused AS ( SELECT id, sum(1.0 / (60 + rank)) AS rrf FROM (SELECT * FROM dense UNION ALL SELECT * FROM lex) u GROUP BY id ) SELECT c.*, f.rrf FROM fused f JOIN searchable_chunks c ON c.id = f.id ORDER BY f.rrf DESC LIMIT 40;

Sharp edge: the lexical arm is under-firing.

Postgres' simple config does not stem and does not remove stopwords. websearch_to_tsquery ANDs every term, so a normal question becomes:

websearch_to_tsquery('simple', 'What is the hostel refund policy?') → 'what' & 'is' & 'the' & 'hostel' & 'refund' & 'policy' → 0 rows

No chunk contains all six lexemes, so the lexical list is empty and RRF quietly degenerates to dense-only. This is visible in the trace above: Retrieve → lexical 0 rows. The design is right; the query builder is too literal.

You can see it in GET /api/search?q=…: conversational questions return dense-only hits. Short keyword queries still match when every term happens to occur in one chunk, which is why this survived casual testing.

Fix → strip stopwords before building the tsquery, or fall back to an OR query when the AND returns nothing. Keep the stored tsv as simple. No migration, no re-index.

4.3 Prompt assembly

The context lives in the user message.

Retrieved text is untrusted input. Concatenating it into the system prompt would let a malicious PDF rewrite the rules. So the rules stay fixed, and the passages are wrapped in <context> inside the user turn — the injection boundary.

sanitise() strips lines beginning system: or assistant:, and removes <|im_start|> / <|im_end|> tokens before insertion.

4.4 Citations

A citation is a substring, not a promise.

After the stream, Bloo reads the [n] markers the model actually used, then picks a sentence from each cited chunk by query-term overlap. The picker respects abbreviations (B.Tech, Rs.), strips the breadcrumb, and caps the quote at 320 characters.

The quote is a slice of stored text. It is not generated, so it cannot be fabricated. The unit test asserts exactly that:

// crates/bloo-rag/src/retrieve.rs assert!(chunk.text.contains(&quote)); // and: kind == "pdf" ⇒ url is None
chunk text · quote highlighted

Refund Policy

Refunds are pro-rata and require a written application to the hostel warden within 30 days of vacating the room. The security deposit of Rs 5,000 is refunded in full after room inspection. Tuition fees are non-refundable after the second week of the semester.

stored_text.contains(quote) → true

Only markers the answer used become cards — four chunks in context often produce one citation. THX-01 can extract the span, but that pass costs 2–3 s on CPU, so it is opt-in; the deterministic picker is the default.

4.5 Refusal

Refusing is a designed outcome.

There are three exits before generation: an empty question, a confident chitchat route (≥ 0.8), and a best dense similarity below 0.40. The last one is the important one.

The refusal path never constructs an LLM request. It costs ~250 ms, returns zero citations, and has no hallucination surface at all. A wrong answer costs more than “I couldn't find that.”

I couldn't find that in the campus documents. Please check with the admin office.
gate, in coderetrieve.rs
const MIN_SIMILARITY: f32 = 0.40; const CONTEXT_CHUNKS: usize = 4; const MAX_CITATIONS: usize = 4; if !fused_nonempty || best_similarity < MIN_SIMILARITY { return Ok(Prepared { refusal: Some(REFUSAL), .. }) } // chitchat ≥ 0.8 returns a greeting before this

The threshold is a product decision, not a model output. It trades recall for precision: better to say “not in the documents” than to answer from the model's general knowledge.

Every choice has a bill.

These are the decisions a reviewer will probe. Each one names the alternative that was rejected and the cost that was accepted, because “we used X” is not an architecture.

08 The viva

Eight questions you will
actually be asked.

Open with this · 3 sentences

Bloo is a retrieval system with an LLM at the end, not a model trained on campus data. Every answer is assembled from four published passages fetched by a hybrid pgvector + full-text query and fused with reciprocal rank fusion. The model may only paraphrase those passages, and every citation is a substring of the chunk it names — so it cannot be fabricated.

Is it fine-tuned?

No. Zero training. The corpus is data, not weights, so publishing or unpublishing a document takes effect on the next query. That is also why there is no “model update” step.

How do you stop hallucinations?

Four layers: only published chunks are visible; context lives in the user message, not the system prompt; every citation is a stored substring with a test asserting it; and a cosine floor refuses when retrieval has nothing. A grounding verifier is designed but not wired yet — say that plainly.

Why not paste everything into a long-context model?

Cost scales per query, latency grows, relevant text gets diluted, and you still cannot prove which sentence supported a claim. Unpublishing would also require rebuilding every prompt. Retrieval is cheaper and auditable.

Why hybrid search?

Embeddings catch paraphrase and miss exact tokens; full-text catches CS-301 and ₹ amounts and misses paraphrase. RRF fuses on rank, so incomparable scores never need normalising. Current caveat: the lexical query ANDs stopwords under the simple config, so it under-fires — the fix is a query-side stopword filter.

Why does it refuse sometimes?

Because the best dense similarity is below 0.40 or nothing was retrieved. A confident wrong answer about fees is worse than “I couldn't find that.” The threshold is a deliberate precision-recall trade, not a failure.

How do you know retrieval is good?

With a golden set: hit@5, recall@10, MRR and refusal accuracy, plus citation precision — the fraction of quotes that appear verbatim. The harness is WP-07 and is not built yet; until then the claim is architectural, not empirical.

What is actually slow?

The LLM gateway's first token: 3.1 s measured. The pipeline Bloo controls is ~235 ms on the critical path, and routing runs concurrently with retrieval. Refusals take ~250 ms because they never call the model.

What breaks at ten times the corpus?

HNSW recall and RAM, and CPU-bound embedding during ingest. Retrieval is isolated in store.rs, so a dedicated vector service would replace that module, not the pipeline. The 384-d index is roughly 220 MB at 150k chunks — one Postgres still fits.

If they remember one thing

The model never sees the campus. It sees four passages — and every citation it returns can be found inside them.
